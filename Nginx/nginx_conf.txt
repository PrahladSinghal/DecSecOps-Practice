Content Security Policy (CSP) is a security feature that helps prevent various types of attacks such as Cross Site Scripting (XSS) and data injection attacks by specifying which dynamic resources are allowed to load on a web page. By using CSP, you can specify where resources (such as scripts, images, stylesheets, etc.) can be loaded from, thereby mitigating the risk of malicious content being injected into your web application.

How CSP Works:
CSP works by allowing the website owner to define a policy through HTTP headers or <meta> tags that tells the browser what content sources are trusted. Any resources that are not from trusted sources are blocked, helping to prevent unauthorized access to the site or malicious activities like script injection.

CSP Syntax:
CSP policies are typically delivered via the HTTP header Content-Security-Policy or the <meta> tag in HTML. The policy defines a set of directives that specify which resources are allowed to load and how they should be handled.

Example HTTP header:

http
Copy
Content-Security-Policy: default-src 'self'; script-src 'self' https://apis.example.com; style-src 'self' https://fonts.example.com
In the example above:

default-src 'self';: This is the default policy for loading resources (such as images, media, etc.), which in this case is restricted to the same origin as the page ('self').

script-src 'self' https://apis.example.com;: JavaScript files are allowed only from the current domain ('self') or https://apis.example.com.

style-src 'self' https://fonts.example.com;: Stylesheets are allowed only from the current domain ('self') or https://fonts.example.com.

Common CSP Directives:
Here are the common directives used in a CSP policy:

default-src: Specifies the default policy for all resource types (e.g., scripts, images, styles) unless otherwise specified by another directive.

script-src: Defines where scripts can be loaded from (JavaScript files).

style-src: Defines where styles (CSS) can be loaded from.

img-src: Specifies where images can be loaded from.

Types of URI Matching in the location Block
There are several types of URI matching methods that Nginx supports within the location block. The matching rules dictate how the location block processes requests.

1. Prefix String Matching (Basic)
Description: The simplest form of matching is by prefix, where the location block matches any URI that begins with the specified string.

Syntax: location /prefix/

Example:

nginx
Copy

    root /var/www/images;
}
This will match any URI that starts with /images/, e.g., /images/pic.jpg.

2. Exact String Matching
Description: If you need to match the exact URI (not just a prefix), you can use an equal sign (=) at the beginning of the location block.

Syntax: location = /exacturi/

Example:

nginx
Copy
location = /about.html {
    root /var/www/html;
}
This will only match the exact path /about.html and not /about.html/ or any other path.

3. Regular Expression Matching
Description: You can use regular expressions to match more complex URI patterns. These locations are denoted by using ~ (case-sensitive) or ~* (case-insensitive).

Syntax: location ~ /regex/ or location ~* /regex/

Example:

nginx
Copy

    root /var/www/images;
}
This will match requests for image files with extensions .jpg, .jpeg, .png, or .gif.

4. Prefix Matching with Trailing Slash
Description: If a URI ends with a /, Nginx will search for locations with a matching prefix that also ends with a /. This can be used to ensure that subdirectories are properly handled.

Example:

nginx
Copy

    root /var/www/data;
}
This would match /files/, /files/docs/, /files/pics/, etc.

5. Most Specific Match
Description: Nginx follows a hierarchy for matching location blocks, and it applies the most specific match. The order of checking for matches is as follows:

Exact string match (=) has the highest priority.

Regular expression match (~ or ~*).

Prefix string match.

Example:

nginx
Copy

    root /var/www/html;
}

location / {
    root /var/www/public;
}
The first location = / matches exactly /, while the second one matches any other requests, including /index.html. The most specific match will always be applied.

Key Directives Used in Load Balancing Configuration

proxy_pass: Forwards requests to the backend server(s).

proxy_set_header: Modifies or sets headers passed to the backend servers.

X-Real-IP: Passes the client's real IP address to the backend.

X-Forwarded-For: Adds the original client's IP to the X-Forwarded-For header for proxy chains.
